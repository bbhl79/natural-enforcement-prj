# 工程基座环境架构：无 bind 烘焙镜像

- 状态：accepted
- 日期：2026-11-25
- 决策记录：[Spec-工程基座](https://github.com/bbhl79/natural-enforcement-prj/issues/23) 硬不变量 3；实施票 [#56](https://github.com/bbhl79/natural-enforcement-prj/issues/56)；原型实证 #11/#12（`prototype/foundation-slice-1` NOTES.md）

## 决策

开发环境采用**无 bind 烘焙镜像架构**：源码经 `devenv/workspace.Dockerfile` 分层
（manifest → deps → 源码）COPY 进镜像，compose 只挂命名卷（pgdata、turbo-cache），
零宿主端口（web 经 `devenv web` 显式 opt-in 是唯一例外）；API/数据库等调试访问
一律经 `devenv exec/shell/logs` 进入容器，不开放调试端口。源码消费型命令
（up/test/lint/typecheck/verify/migrate*/seed/web）前置增量重建 workspace 镜像
（层缓存命中时秒级），"改完即测"是命令面内建语义。

## 背景

- 开发机容器引擎是 podman machine（独立虚拟机）：bind mount 的宿主路径会解析进
  machine 自身文件系统——原型 #11 实测挂 `/home/.../natural-enforcement-prj` 进容器
  得到的是 machine 里一份旧同名目录，**不报错、内容全错**，对 agent 是最危险故障类别。
- Windows（WSL2）与 macOS 的虚拟机文件共享实现差异最大；无 bind 使架构不依赖
  任一平台的文件共享层。
- 多 agent 并发：零宿主端口使端口冲突整类消失（web 例外经 profile 隔离 + 显式端口）。

## 考虑过的选项

- **bind mount 源码 + 容器内工具链**：拒绝。正是被实证否定的路径（静默挂错）；
  且把"容器内即最新代码"建立在各平台文件共享层的正确性上。
- **要求真 docker engine（弃 podman machine）**：拒绝。Windows 开发机矩阵已验证
  Rancher Desktop WSL 集成（podman engine）；强加引擎要求等于推翻支持环境矩阵。
- **docker cp 同步环 / 挂载单文件例外**：暂不采用。反馈环（重建 + 刷新）受等待
  预算约束已达标；若未来人类高频改前端实测不可接受，按 SPEC 流程重评估。

## 后果

- **代价（如实）**：前端无 HMR——反馈环 = 重建 + 刷新；新增 workspace 包触发依赖
  层重建（成本受预算约束，deps 缓存优化结论的采纳归 #58）。
- 运行容器以 root 运行是当前开发环境取舍（镜像内容物 root 属主，uid 化全线
  EACCES，原型 #11 实测）；dev 单机场景无安全边界损失，卷内容不回宿主。
- "容器内代码 = 当前工作树"由 ensure_fresh_workspace 保证来源一致性；固定输入
  快照与不可变镜像绑定（防同 worktree 构建竞争）归 #58，本 ADR 不声称完整构建证明。
- 未来若需开放调试端口，须显式修订 Spec-工程基座 硬不变量 3。
