# 0007 管理用户不拆成三个角色

Status: accepted（2026-10-13）

等保三级要求管理用户权限分离，并设立系统管理员、审计管理员、安全管理员三类职责。基层往往只有很少的人维护系统。2026-10-13 定案：软件里只保留「系统管理」这一个角色族来承载管理台的维护权。三类职责写在业主方的职责文件里。服务端允许同一人员持有全部维护权。监督评查可以查阅和导出其数据范围内的管理台审计，不能维护，也不能打开人员主数据。

这样做是为了少做角色维护。权限分离不在软件里强制。

细则在 [管理台：管理用户分权的岗位切分与互斥](https://github.com/bbhl79/natural-enforcement-prj/issues/86) 的决议。本篇只记为什么这样定。

## Considered Options

- 在系统管理族内设三个互斥角色。否决。同一人员不能兼持授权与审计，角色维护变重。业主方的职责文件承担这道分离。
- 把系统管理拆成三个角色族。否决。六族会变成八族。矩阵票的题目是六族。
- 审计只读只给系统管理。否决。区里的监督员要能查是谁停用了本区人员。
- 监督评查可以打开人员列表和卡片。否决。人员主数据会多一条查阅通道。审计里写工号，足够回答是谁做的。
- 审计事件写入登录标识或执法证号。否决。监督评查读审计时会收集到手机号和证号。
- 监督评查不能导出审计。否决。检查组要拿走本区本月的变更记录。
- 只让监督评查看认证和人员维护的审计。否决。只读再按对象拆开，又变回分档。

## Consequences

- 矩阵不设互斥行。系统管理允许：组织、参照数据、人员与登录凭据、配置类对象的维护，被锁账号列表、解锁、重设初始口令，以及管理台审计的查阅和导出。监督评查只允许查阅和导出管理台审计。其余四族不写这些允许行。操作码名字归 [认证：角色族×操作码矩阵定案（六族×24 操作码）](https://github.com/bbhl79/natural-enforcement-prj/issues/71)。
- 一人可以同时持有系统管理与办案类角色。有效权限取并集。沿用 [0005 权限底座沿用人员与角色权限表](0005-权限底座沿用人员与角色权限表.md)。
- 监督评查的只读覆盖数据范围内的全部管理台审计：认证与授权拒绝，人员的创建、停用、恢复、解锁、重设初始口令，组织维护，参照数据维护，配置变更，人员查阅。导出范围与只读相同。导出留痕。查阅也留痕。
- 数据范围沿用现有定义。事件有所属机构时，按对象所属机构过滤。
- 没有机构锚点的配置变更，谁能看见，本篇不定。[0006 配置类对象共用一套版本与批准](0006-配置类对象共用一套版本与批准.md) 已把「同一范围」留给各业务票，没有给审计一个机构锚点。
- 人员列表和单张卡片在响应含登录标识或执法证号时留痕。不限次。事件写工号、动作、时间、成败。不写登录标识，不写执法证号。配置变更前后值里的口令、密钥、登录标识、执法证号不进入事件。形状已由 [0011 认证留痕写入共用表](0011-认证留痕写入共用表.md) 定案。承载与认证、配置变更、业务操作共用一种留痕，见 [全局契约：不可篡改与追加式记录的全局保证策略](../global-contract-immutability.md)。
- 文书模板的批准人仍可由业务票另授。那是在系统管理这行之外追加允许。操作码仍按 [0006](0006-配置类对象共用一套版本与批准.md) 按对象拆开。
- 系统不建立安全管理员、审计管理员、系统管理员三个角色，也不检测同一自然人是否跨职责兼任。
- 术语沿用 `GLOSSARY.md` 的「系统管理」「人员」「工号」「登录标识」「执法证号」。不新增词。
