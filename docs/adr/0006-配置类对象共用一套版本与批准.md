# 0006 配置类对象共用一套版本与批准

Status: accepted（2026-10-13）

勘误（2026-10-19，[#105](https://github.com/bbhl79/natural-enforcement-prj/issues/105) 团队待办 7-16）：正文的「监督评查」即 `GLOSSARY.md` 的「监督」角色；正文不改。

文书模板、校验规则、工作日历、统计指标口径都会换版，在办事项要不要跟着换也各不相同。2026-10-13 定案：这四类共用一套门。一次变更留下新版本；批准时写明生效日，以及在办事项的三种处理之一，到了生效日才成为当前生效版本；提交和批准可以是同一个人。同一范围同时只有一个当前生效版本，另至多一版已批准、未到生效日的预定。录入要件不走这套门。

等保三级要求配置变更在实施前经过审批。没有这道审批，可以判高风险，而且没有补偿措施。所以批准记录留下。不要求另一个人来批，是因为那条要求写的是审批程序，不是维护人员的人数。

细则在 [管理台：配置类对象的生效与版本化契约](https://github.com/bbhl79/natural-enforcement-prj/issues/82) 的决议。本篇只记为什么这样定。

## Considered Options

- 按对象种类各做一套，或按「会不会改到在办事项」分成两套。否决。那些业务票还没选定在办事项跟不跟新版。先拆开，等于替它们作答。
- 不设批准，保存即成为当前。否决。配置变更会没有审批记录，与 [研究票：管理用户分权与配置变更留痕的等保三级口径查证](https://github.com/bbhl79/natural-enforcement-prj/issues/76) 冲突。
- 批准必须由另一个人做。否决。同一次变更就要两名人员。基层可以只有一名持有系统管理角色族的人员。
- 同一范围可以同时排上多版未来才生效的版本。否决。到了生效日，哪一版成为当前要另写规则。下一次换版，有一版预定就够。
- 作废当前版本时，自动把上一版设回当前。否决。正在用的模板会在没有人批准的情况下被换掉。
- 版本写上失效日，到点自己停用。否决。正在用的规则会在没有人操作的情况下被拿掉。要在某一天接上新版本，用那一版预定。
- 指回旧内容时，复制出一个内容相同的新版本。否决。以后调卷，分不清当时用的是哪一版。
- 四种对象共用一套操作码。否决。文书模板的批准人与工作日历的批准人可以不是同一批人。
- 录入要件一并版本化。否决。录入要件是一条线索按其渠道与法域在录入时应当呈现的那些项，不是按版本生效的配置类对象。

## Consequences

- 在办事项的处理只有三种：只约束此后新发生的事项；在办事项改用新版本；在办事项继续用它已经绑定的版本。各业务票从中选择。「同一范围」按哪些字段划，也由各业务票定。
- 指回旧版本就是再批准一个尚未作废的旧版本。作废后的版本保留，但不能再被批准为当前。作废掉当前版本后，该范围暂时没有当前生效版本。
- 操作码按 `cfg.<对象>.<动作>`。动作是提交、批准、作废、撤回、查看。标识符怎么拼，归 [认证：角色族×操作码矩阵定案（六族×24 操作码）](https://github.com/bbhl79/natural-enforcement-prj/issues/71)。角色族不拆成三员，系统管理与监督评查各允许什么，见 [0007 管理用户不拆成三个角色](0007-管理用户不拆成三个角色.md)。
- 留痕与认证、业务操作共用一种记录。尚未批准的版本可以改同一版正文。已经提交后又改字，该次提交失效，须重新提交。见 [全局契约：不可篡改与追加式记录的全局保证策略](../global-contract-immutability.md)。批准之后，版本内容不能改。
- 参照数据先不入这套门。是否入门，等 [管理台：参照数据的承载形态定案](https://github.com/bbhl79/natural-enforcement-prj/issues/78)。
- 术语见 `GLOSSARY.md` 的「配置类对象」「录入要件」。
