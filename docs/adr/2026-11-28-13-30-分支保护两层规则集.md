# 分支保护两层规则集：绕过只解禁审批层，基础层对所有人恒立

- 相关：[GitHub App 认证入口](../../docs/agents/github-app-auth.md)、[per-worktree 运行资源隔离](2026-11-25-22-30-per-worktree运行资源隔离.md)

## 背景

Spec §7 要求 dev 分支保护为「两层规则集」：基础层（必须 PR + 必需检查，无日常
绕过身份）+ 审批层（一个批准、点名指挥者账号、绕过仅限 PR 使用）；新推送使旧
批准失效；管理员仍可改规则（防日常误用，不剥夺所有者最终控制）。验收前仓库
只有一个单层规则集 `protect-dev`（PR + 1 批准，无必需检查、无 dismiss-stale、
无绕过名单）。#71 已交付 CI 质量门（check 名 `quality-gate`），但必需检查成为
受保护分支必需项被明确排除在 #71 之外（「CI 绿 ≠ 自动阻止合入」）。

## 决策

1. **两个独立规则集而非一个**：`protect-dev-base`（deletion + non_fast_forward
   + pull_request(0 批准) + required_status_checks(`quality-gate`)，**无任何
   bypass_actors**）与 `protect-dev-approval`（pull_request(1 批准 +
   dismiss_stale=true)，bypass_actors 仅 `[User bbhl79(3615225),
   bypass_mode=pull_request]`）。绕过名单是规则集级属性——审批层可被点名指挥者
   在 PR 合入时绕过，而基础层的 PR/检查要求**没有任何绕过者**：即使绕过权被
   误配成 `always`，直推/强推/删分支仍被基础层拒绝（纵深防御）；「检查失败仍
   拒」「指挥者本人直推仍拒」由同一结构免费成立。单规则集做不到这一点。
2. **保存配置即代码 + CI 常驻漂移核对**：4 份规则集 JSON 保存在
   `devenv/rulesets/`（dev 两层持久 + 验收期测试分支 transient 对）；
   `devenv branch-protection` 拉取实时规则集与保存配置逐字段比对（匿名只读；
   `BP_GITHUB_TOKEN`/`GITHUB_TOKEN` 存在时优先），漂移或无法核查即非零
   （fail closed），并作为 quality-gate 的 CI 步骤常驻。效果是**自锁闭环**：
   规则集要求检查绿才能合入，而检查里有一项「保护配置不得漂移」——削弱保护
   会使必需检查变红，PR 无法合入。配置变更必须走「PR 改保存配置 + UI 同步
   应用」两步锁齐（先应用 UI 再等 CI 绿，或同步进行），这正是「管理员仍可改
   规则」的受控形态。
3. **App 无 Administration、不在绕过名单（维持 spec 安全基线）**：规则集的
   创建/修改只能由指挥者以管理员身份在 Web UI 完成（API 负载即保存 JSON，
   形态见 `devenv/rulesets/*.json`）；App 对 rule-suites（审计面）也不可读
   （403/404），管理员读取归指挥者本人。`current_user_can_bypass=never` 由
   harness 断言。
4. **受控验收方法论（spec 验收清单项 10 a–i）**：反例（直推/无批准合入/
   bypass 尝试）直接打在真实目标上——**被拒即零写入**，每阶段前后断言
   dev HEAD 不动（AC「所有无效验证均不写入 dev」的机械证据）；两类有真实
   写入风险的正例（指挥者 bypass 合入）与「检查红仍拒」先在**专用测试分支**
   `test/bp-73-acceptance`（同样两层规则的 transient 对）上执行，全绿后才在
   dev 上以交付 PR 自然复现（g=批准失效流程、d=绕过合入、b/c=未批准合入
   尝试）。红探针 PR 用「workflow 静态门禁故意违规」制造确定性 CI 红
   （复用 #71 的 ci-workflows 检查项，doctor 即拒、快速且无副作用）。
5. **审计面如实边界（项 i）**：人类绕过留下的记录**先探测再下结论**——机器
   面（PR 状态/评审 DISMISSED/合并者/时间线/活动事件）App 可读并留证；
   rule-suites（含 `rule_suite_result=bypass` 与 actor 过滤）需 Administration
   读权限，只能由指挥者以本人身份读取并归档；**不预设位置/内容/保留期，不
   声称能区分冒用**（agent 可读人类凭据是已接受残余风险，绕过审计中的
   actor=bbhl79 无法区分真人还是冒用）。

## 取舍与已知边界

- **`strict_required_status_checks_policy=false`**：不强制 PR 分支与 dev 完全
  同步才可合入（避免每次 dev 前进都强制全体 PR 重基线重跑 CI）；「合入的经过
  检查的版本」由 squash 合入 + 检查在 PR head 上执行保证。如需收紧为 true 是
  一行配置 + UI 同步。
- **merge 方法三种皆允许（merge/squash/rebase）**：spec §7 约定 squash 合入，
  但当前 dev 历史实际存在 merge commit（历史实践与 spec 表述有偏差）；本票不
  用规则集机械强制 squash，把该偏差如实记录，收紧与否留给指挥者另行决策。
- **`require_extra_approval_for_unattributed_changes=true`（审批层，沿用现状）**：
  该参数只对 Copilot 开的 PR 生效（官方语义），本仓库无 Copilot PR，保留现状
  以最小化语义漂移。
- **额外规则集检测的漏检边界**：漂移核对按「模式是否匹配 refs/heads/dev」判定
  额外规则集（精确名、`~DEFAULT_BRANCH`、通配形）；用比 `dev` 更窄且不等于
  dev 的 glob 精确覆盖 dev 的规则集不在机械检测范围（如实声明，宁少误报不静默
  漏报的方向上选择了可解释性）。
- **bypass_actors 字段可见性**：规则集单读端点对匿名/App 是否总是返回
  bypass_actors 未预设——字段存在即机械比对；缺失而保存配置预期有绕过者时
  fail closed 判漂移并附人工核对指引（验收时实测记录实际行为）。
- **UI 标签与 API 字段名差异**：Web UI 的规则显示名（如 Block force pushes /
  Require a pull request before merging）与 API 规则类型（non_fast_forward /
  pull_request）不同名；应用以 `devenv/rulesets/*.json` 字段为准，应用后
  `verify-config` 机械核对兜底。
