# 0018 录入要件以代码声明承载

Status: accepted（2026-10-20。Lei Hu 拍板，见 [#24 决议](https://github.com/bbhl79/natural-enforcement-prj/issues/24#issuecomment-6290364664)）

录入要件是「一条线索按其线索来源与法域，在录入时应当呈现的那些项」。2026-10-20 定案：它是一份代码里的声明式常量，前端渲染表单与服务端判定缺件读同一份声明。改动走代码评审和发布。

这样定，是因为用户故事里「共同要素必须完整，差异化要件按场景呈现」要求校验与呈现都按同一份配置走。分头维护两份必然漂移。

## Considered Options

- 存成管理台配置，运行期可改，走 [0006 配置类对象共用一套版本与批准](0006-配置类对象共用一套版本与批准.md) 的门。否决。录入要件不属配置类对象（0006:7 已定「录入要件不走这套门」，:23 已否决「录入要件一并版本化」）。运行期可改还要付新操作码、批准与留痕，并且有「业务人员改出非法流程」的风险。
- 存成参照数据，走 [0016 参照数据随种子只追加写入](0016-参照数据随种子只追加写入.md) 的「业务编码 + 版本」口径。否决。参照数据承载的是取值项（线索来源编码表、违法类型清单、依据条款、裁量分档），要件是结构化声明，搬进表要另造一套「要件项 + 适用条件」的行结构。
- 用规则引擎表达条件。否决。表达式无法静态校验「共同要素必须完整」，也不利于把缺件后果写死在要件项上。
- 按「来源 × 法域」逐格配置。否决。组合会失控。实际是公共、来源、类型三组叠加。

## Consequences

- **一份声明，两个用途**：表单渲染与缺件判定读同一份声明。可测断言是「所有来源与法域的组合下，表单 schema 的必填集合与后端缺件判定的集合完全相等」。
- **要件项的六个属性**：呈现、必填性、必填时机、缺件后果、依据、要件键。依据写「文件编号 + 条号」，指向文件表，见 [0019 依据以文件表引用承载](0019-依据以文件表引用承载.md)。校验规则按要件键引用，不复制要件的内容。
- **缺件后果分两层**：单个要件缺失的后果写在要件项上（阻断、警告、提示）；「这一步整体能否推进」归校验规则，校验规则本体归 #30。
- **老线索按登记当时的必填项判**：登记时在线索上记一行当时的要件键集合。要件清单改版后，新加的要件只对新线索生效。这一行是「这条线索登记过哪些项」的事实记录，不是按版本生效的配置类对象，不违 0006:7。
- **不新增操作码**：`packages/shield/src/contract/opcode.ts` 的 ADMIN_OBJECTS 仍是 template、rule、calendar、metric 四项。
- **留痕靠 git 历史**：要件的改动与代码改动同走一条评审链路，不另设配置变更留痕。
- **类型层尚未产出**：要件按初步涉嫌违法类型分，四个法域的清单分四张票产出，见 #181–#184。
- 术语见 `GLOSSARY.md` 的「录入要件」「线索来源」「标签」。
