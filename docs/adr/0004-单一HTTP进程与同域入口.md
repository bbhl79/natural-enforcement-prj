# 0004 单一 HTTP 进程与同域入口

Status: accepted（2026-10-12）

登录闭环需要一个接收 HTTP 的进程。仓库当时没有这个进程：六个业务模块只是库，浏览器打得开的页面在 `8899`，`8080` 上的 nginx 没有站点配置。2026-10-12 定案：本图的实施切片落地**一个** NestJS 进程，启动时装入全部六个模块；浏览器只访问 `https://localhost:8080`，由这一个 nginx 终结 HTTPS，再按路径转发。

会话 Cookie 和会话守卫要在同一次请求、同一个进程里完成。拆成六个进程会把已经定下的同域会话拆开。细则与两张请求路径图在 [认证：API 应用层归属与形状](https://github.com/bbhl79/natural-enforcement-prj/issues/65) 的决议。本篇只记为什么这样定。

## Considered Options

- 每个业务模块各起一个 HTTP 进程。否决。登录与办案分成多个进程后，每个进程都要自己校验会话，或者再加一个网关。
- 浏览器改走 `https://localhost`（宿主端口 `443`）。否决。`8080` 已经是 compose 里 nginx 的宿主端口。
- 启动代码放进 `backend/identity`。否决。这个进程要同时装入其余五个模块，identity 的依赖规则不允许。
- 启动代码放在仓库根目录 `server/`。否决。要改工作区声明，并让结构测试扫到这个目录。
- 新增第 11 个命令 `dev server`，在宿主机启动进程。否决。依赖会留在宿主机，进程也不在 compose 网络里，nginx 无法按已定的容器内端口转发。

## Consequences

- 新包 `backend/server`。它不是第七个业务模块。结构测试允许它经公共出口引用全部六个模块，包括监督统计。只有这个包里的一个文件可以直接引用身份模块的数据库适配器。`integration/` 仍只做测试装配。
- compose 增加 `server`。镜像名 `natural-enforcement/server:dev`，由 `dev build` 构建，`pull_policy: never`。进程在容器内听 `3000`，这个端口不映射到宿主机。镜像里跑 Node。改代码后重新 `dev build`，新镜像才会被 `dev up` 用上。
- nginx 把 `/` 转到 frontend 容器，把 `/api/` 转到 server 容器。`8899` 不再给浏览器用。页面文件与接口结果在浏览器里接上：浏览器先取页面，再请求同一主机的 `/api/`。frontend 容器不调用 server。
- `/api/health` 不要求会话 Cookie。`dev health` 请求 `https://localhost:8080/` 与 `https://localhost:8080/api/health`，用证书校验 HTTPS。证书文件仍归 [管理台：运行参数与密钥来源约定](https://github.com/bbhl79/natural-enforcement-prj/issues/80)。证书约定落地前，健康检查不能全绿。
- 不新增第 11 个 dev 命令，不引入 Playwright。CI 仍只调用 `./dev check`。HTTP 适配用 Nest 默认的 Express。Express 与 Fastify 的 CSRF 行为已查证为一致，不为此单开一轮。
- 与 [0002 服务端会话记录定案](0002-服务端会话记录定案.md) 衔接：Cookie 仍是 `__Host-sid` 与 `__Host-rm`，守卫仍在办案代码之前填写 `ActorRef`。
