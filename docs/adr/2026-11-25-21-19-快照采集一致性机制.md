# ADR：快照采集一致性机制（stat 括号）与成立条件

- 日期：2026-11-25
- 状态：已接受（#58 评审缺陷三修复；残余风险待指挥者确认，见 §5）
- 相关：#58（保证构建快照与运行镜像一致）、#23 Spec-工程基座 §3、docs/evidence/58-snapshot-immutable/

## 1. 背景与问题

#58 要求：采集或构建期间工作树再变时，本次使用**完整旧快照**或**明确拒绝重试**，
**不产生混合内容却报告来源一致**。

第一版实现用「连续两次 `git add -A` + `write-tree` 相同」作为一致性判据。评审
指出其不成立：两次全量读取读到相同字节，只证明两次读取之间内容没**净变化**，
不能证明这些文件曾**同时**属于一个完整工作树状态——

- **跨文件混合**：写者先写 A 后写 B，两次采集都读到 (A新, B旧)，而该组合从未
  同时存在于磁盘；
- **单文件撕裂**：采集读到写了一半的文件（非原子写），两次采集读到同一份撕裂
  内容。

「快照哈希与镜像内容一致」也不能替代本证明——它只说明镜像忠实于快照，不说明
快照本身不是混合体。

## 2. 决策：stat 括号采集（stat-bracket capture）

单次采集用 文件清单 + 逐文件 `(mtime, size, inode)` 的 stat 括号夹住读取窗口：

```text
capture_once:
  files1 = git ls-files -c -o --exclude-standard      # 候选文件清单
  stats1 = stat(files1)                                # mtime(ns)+size+inode
  T      = git 临时索引 add -A + write-tree            # 实际读取+哈希
  stats2 = stat(files1); files2 = ls-files 复核
  if stats1 != stats2 or files1 != files2: 不稳定 → 重试
  else: 接受 T
capture: 最多 3 次；均不稳 → 明确拒绝（exit 4）
```

**成立论证**：若括号两端 清单与全部 stat 完全相等，则读取窗口内没有任何文件
发生（可检测的）写入——每个文件被读到的字节在整个窗口内稳定，因此树 T 等于
窗口内任一时刻的完整工作树状态（即「完整旧快照」）。若窗口内有写入，stat 或
清单必变 → 重试；写者不停 → 明确拒绝。两条验收允许路径（完整旧快照 / 明确
拒绝） thus 闭合，混合内容不被接受。

**为什么不用双采集**：stat 括号严格更强——双采集对「窗口内写入但净内容不变」
（写后恢复、mtime 秒级粒度内的同尺寸覆写）不可见，stat 括号对 (mtime, size,
inode) 任何变化可见；且单次括号通过即满足一致性，无需第二次全量读取。

## 3. 覆盖的写入者（成立条件）

以下写入都会改变 (mtime, size, inode) 至少一项，**全部被检出**：

- 原子重命名保存（vim、VSCode、JetBrains、sed -i 的默认方式）：新文件 → 新 inode + 新 mtime；
- 原地写 / 截断重写（`>`、编辑器非原子模式）：mtime + size 变化；
- 追加（`>>`、日志式写入）：mtime + size 变化；
- 新建 / 删除 / 改名：文件清单变化；
- `cp -p` / `touch -r` 恢复 mtime：inode 仍变（新文件），检出。

mtime 用纳秒（GNU stat `%y`；macOS 经 coreutils `gstat`，已在宿主白名单）。

## 4. 不覆盖（明确声明的残余孔洞）

1. **mtime 保持型原地覆写**：`rsync -a --inplace` 且尺寸不变这类「内容变、
   (mtime,size,inode) 全保持」的写入——用户态无 fs 快照/inotify 无法检出。
2. **窗口内 ABA**：同一文件在一次采集窗口（~50ms）内 A→B→A 且 stat 复原——
   需要写入者刻意对抗，诚实编辑器/构建工具不产生。
3. **非本地文件系统语义**：9P/网络盘（如仓库放 /mnt/c）的 mtime/inode 语义
   不保证——本基座要求仓库在 WSL2 ext4 / macOS APFS 本地卷。

## 5. 需要指挥者确认的取舍

普通编辑器/构建工具的**自由写入**与验收第二条在本机制下可以同时保证（§3 全
覆盖）。残余孔洞（§4.1/4.2）的关闭需要引入宿主 inotify/fanotify 监听（新宿主
依赖，macOS 需 fswatch）或文件系统级快照（btrfs/APFS，WSL2 ext4 不可用）——
均显著增加基座复杂度。**建议接受 §4 声明为残余风险**；若指挥者要求关闭，
另开票评估 inotify 方案。本 ADR 不声称「任意写者下绝对不混合」。

## 6. 确定性验证（不撞概率）

离线测试经 `snapshot_test_hook` 测试缝在读取窗口内注入**确定性**写入
（devenv/test/snapshot-offline.test.sh S23/S23b）：

- 两个关联文件 a/b 交替更新：第 1 窗口只写 a（制造 (v2,meta-v1) 混合窗口），
  第 2 窗口补写 b——断言最终只接受完整版本 (v2,meta-v2)，且两个混合组合
  （独立计算的树哈希）均未出现；
- 每个窗口都写入——断言 3 次后明确拒绝（exit 4）。

真实引擎侧证据（持续写入拒绝、构建期修改不泄漏、被接受快照与镜像内容对账）
见 docs/evidence/58-snapshot-immutable/。
