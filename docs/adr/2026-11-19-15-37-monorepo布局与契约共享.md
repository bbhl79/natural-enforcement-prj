# monorepo 布局与契约共享：apps/packages 分层 + zod-first 契约包

- 状态：accepted
- 日期：2026-11-19（2026-11-21 随 #11/#12 原型实证修订；2026-11-22 按 #23 同步「决策」段）
- 决策记录：[Grilling-monorepo布局与契约共享](https://github.com/bbhl79/natural-enforcement-prj/issues/9)

## 决策

仓库采用 `apps/`（可运行产物）与 `packages/`（被依赖库）两层划分：`apps/web`（React+Vite+RTK Query）、`apps/api`（NestJS+Prisma）、`apps/e2e`（Playwright 执行器 + 探索引擎编排，独立服务）；共享面只建 `@ne/contracts` 与 `@ne/tsconfig`，不建 `ui`/`utils`/`eslint-config`，直到出现第二个消费者。

契约共享采用 **zod-first 共享包**：`@ne/contracts` 的 zod schema 是唯一事实源，导出 schema、`z.infer` 类型与路由常量；API 请求用同一 schema 经自写 `ZodValidationPipe` 做运行时校验，NestJS 12 原生 Standard Schema 支持仅用于响应序列化；`@nestjs/swagger` 12 用于派生 OpenAPI 构建产物，供文档与 Schemathesis 契约探索，但请求体 schema 派生尚有断点，修复并通过完整性验收是 Schemathesis 契约探索（P1）的前置条件，归 [Spec-工程基座](https://github.com/bbhl79/natural-enforcement-prj/issues/23) 解决；web 用推断类型手写 RTK Query endpoint；e2e 用类型 + zod 校验响应。

全仓 ESM（`"type": "module"`），TypeScript 配置按运行时分层：Node 包使用 `module/moduleResolution: nodenext`，浏览器包使用 `moduleResolution: bundler` 并启用 JSX 与 DOM lib；contracts 只产 ESM dist。

## 背景

- 1 人类 + 多 agent 并发开发；宿主机只存代码、devenv 唯一入口；技术栈已锁定 React/Vite/RTK Query、NestJS 12、Prisma 7、TypeScript 6、Node 26。
- 契约是前后端与 e2e 唯一的跨 app 写面，方案必须服务「契约先行、多个 agent 并行」。

## 考虑过的选项

- **OpenAPI 为中心 + 前端 codegen**：拒绝。契约源在 API 实现里，前端 agent 要等后端；生成物新鲜度需要额外门禁；`@rtk-query/codegen-openapi` 最新 npm 2.2.0 已约 11 个月未发版、未声明 RTK 2.x 兼容，维护风险高。OpenAPI 在本方案中仍是派生产物，文档与 Schemathesis 不受影响。
- **混合（zod 源 + OpenAPI + 前端 codegen）**：暂不采用。比 zod-first 多一条生成链；未来若明确需要自动 hooks，可在本方案之上增量加 codegen，契约源不用改。
- **tRPC**：拒绝。把消费者绑到 TS router，切断 e2e 的 Python/Schemathesis 与外部消费者；与基于 OpenAPI 的契约探索路线冲突。
- **纯 TS 类型包**：拒绝。类型运行时被擦除，API/e2e 需要运行时校验；会导致类型与校验两套来源漂移。
- **拆分 `packages/e2e-cases`**：暂不拆。用例不被其他 workspace 消费；Playwright `testDir` 单点配置最简；未来需要独立版本化/外部消费时再拆。
- **contracts 直出 TS 源码**：拒绝。NestJS tsc/Jest 对跨包 TS 源码的 rootDir/transform 摩擦大；contracts 含 zod 运行时，必须有 JS 产物；dist 是 Vite/tsc/Playwright 三套工具链的确定性最小公倍数。
- **契约变更加锁/排队**：拒绝。串行化成本高于实际冲突率；用「加法优先 + 破坏性同 PR 改齐 + 领域分文件 + issue 声明」替代。

## 后果

- 依赖边界（apps → packages 单向、apps 互不依赖、contracts 不依赖框架）是逻辑边界：pnpm workspace 共享同一 node_modules 链接空间与文件系统，相对路径/TS paths 可绕过包解析；必须由 ESLint `no-restricted-imports` 门禁（纳入 `devenv verify`）执行。
- NestJS 12 与 Prisma 7 均为 ESM-only，故全仓 ESM；ESM 相对导入需 `.js` 扩展，写入 AGENTS.md 约定。
- **Standard Schema 实测结论（#11 原型落定）**：NestJS 12 的 Standard Schema 支持作用于**响应序列化**（拦截器），请求校验不生效；请求校验采用自写 Zod 管道（原兜底方案成为主线），不引入 nestjs-zod。**swagger 请求体派生存在断点**（#11/#12 遗留）：OpenAPI 请求体 schema 派生不完整，是 Schemathesis 契约探索（P1，backlog #17）的前置条件，归 Spec-工程基座 解决。
- 契约是传输层 DTO，不是 Prisma 模型；DB 模型与契约之间的映射留在 `apps/api`。
- 改 contracts 后消费者需重建；turbo 缓存缓解。**turbo 运行期 EACCES（#11 实证）**：容器内 turbo 运行期权限问题，任务编排回退 `pnpm -r`；turbo 缓存层保留，运行器选型归 Spec-工程基座。
- **catalog 精确 pin（#12 实证）**：lockgen 全量重解析会使 `^` 范围静默漂移（@nestjs/common ^12.5.1 漂 12.6.0），catalog 版本一律精确 pin，不用范围。
