# 0015 新口令不得与最近五次口令重复

Status: proposed（2026-10-17，Lei Hu 2026-10-17 18:56 授权提交）

现在只拦「新口令等于当前口令」，而且只在本人改密时拦（`backend/identity/src/domain/password-policy.ts:10`、`:133`）。系统管理重置口令不比较旧口令。

[#68](https://github.com/bbhl79/natural-enforcement-prj/issues/68) 定案（2026-10-12）写的是「历史口令不重复：一期不做（非测评核查项，且需新增表）→ 移交系统管理模块」。Lei Hu 2026-10-17 18:12（UTC+8）拍板推翻了这一句，上下文见 [#75 回写评论](https://github.com/bbhl79/natural-enforcement-prj/issues/75#issuecomment-6232717997)，#68 上也有对应注记（[#68 评论](https://github.com/bbhl79/natural-enforcement-prj/issues/68#issuecomment-6232726338)）。定案内容：一期就做；新口令不得与历史口令重复；只存历史口令的散列；本人改密（含首登和到期强制改密）和系统管理重置口令都要校验，与 #68「一个校验器、两处入口」是同一道；记几次由团队定，工程主管定为最近 5 次。#68 的其余定案值不变。

这样做是为了让人员不能靠改回旧口令绕过 90 天强制改密。

## 与等保口径的关系

7-2 的原文见 [#105 评论](https://github.com/bbhl79/natural-enforcement-prj/issues/105#issuecomment-6228998900)：「停用、恢复、改角色**不做双人复核**；等保风险暂时不考虑。」#105 正文待拍板表也记了这一条。仓库文件里没有 7-2 的出处，这一点出处待补。本篇是 Lei Hu 单独点名要做的一条功能，不表示等保要求整体纳入一期，也不据此重开 7-2 或其他等保项。#68 当时记的「非测评核查项」仍然成立，本篇不作为等保应答依据。「历史 5 次不重复」这个数值和 `docs/research/password-policy-lockout.md:16` 的通行口径一致，只作为参考，不是定次数的依据。

## Considered Options

- 只比当前口令，也就是维持现状。否决。改两次就能回到原口令。
- 存历史口令的可逆密文或明文。否决。只存散列（Lei Hu 定）。
- 历史散列用一个统一的盐，或者另选一种算法。否决。那样做和当前口令不是同一强度。离线比对时，一次计算就能命中所有人。
- 把历史放进 `Personnel` 的一列数组。否决。只追加的触发器管不到单列，取最近 N 条也要整列改写。
- 历史写进 `AuditTrail`。否决。ADR 0011 规定口令不进留痕的任何一列。
- 5 次不含当前口令（当前 + 之前 5 次，共 6 个散列）。否决。团队提议「最近 5 次」包含当前口令，与 `password-policy-lockout.md:16` 的通行说法一致，计数方式也不用额外解释。这一条是团队定的，Lei Hu 授权团队定。
- N 做成配置类对象或运行参数。否决。ADR 0006 的批准门只收文书模板、校验规则、工作日历、统计指标口径四类。ADR 0008 规定运行参数不在管理台编辑。口令策略的阈值现在是硬编码（`password-policy.ts:1`），#91 也把「策略参数可配置」列为不做。

## Consequences

- **算法**：历史散列和当前口令用同一个函数生成，即 `CredentialService.hashPassword`（`backend/identity/src/services/credential.service.ts:27`）。参数是 `ARGON2_OPTIONS`（`:13-18`）：argon2id、内存 19456 KiB、迭代 2 次、并行度 1，库为 argon2 0.45.1（`infra/VERSIONS.md:49`）。每条都是 PHC 串，自带随机盐。比较时逐条调用 `verifyHash`（`:32`，即 argon2 `verify`），不比较散列串，也不重新计算散列去对比。旧参数下生成的历史条目照样能验证，因为参数写在串里。
- **口径**：新口令不得与「当前口令 + 最近 4 条历史」中的任何一个相同，共比较 5 个散列。常量 `PASSWORD_HISTORY_DEPTH = 5` 放在 `password-policy.ts`，和其他阈值放在一起。
- **入口**：本人改密（`backend/server/src/auth.service.ts:336-343`）、系统管理重置口令（`backend/server/src/admin.service.ts:117-122`）、恢复时重置初始口令（#105 D7）都要校验。登记新人员和引导首个系统管理人员时，该人员还没有历史，不用比。登录时按新参数重算当前散列（`credential.service.ts:42-53`）不是换口令，不写历史，也不校验。
- **拒绝**：沿用口令策略现有的返回形状，即 400 `{ result: 'non-compliant', rules }`（`admin.service.ts:26`、`:118`，`auth.service.ts:120`、`:341`）。仓库里 409 用于业务状态冲突（#105 停用、唯一冲突），不用于口令内容不合规；仓库里也没有用 422 的先例。历史比对只在其余口令规则全部通过后才做，省掉不必要的 argon2 计算。
  - 本人改密：命中历史返回规则码 `reused`，因为本人知道自己的历史口令。新口令等于当前口令时仍只返回 `same-as-current`（`password-policy.test.ts:95` 现有断言不变）。
  - 系统管理重置口令、恢复时重置初始口令：命中历史（含当前口令）时，响应里不出现 `reused`，只返回通用码 `unavailable`，界面显示「此口令不可用，请换一个」。码名沿用现有规则码的形容词式短横线写法（`too-short`、`common`、`repeated`，`password-policy.ts:2-11`）。理由：重置时提示「重复」，等于告诉管理员这串是对方最近用过的口令。不加次数限制。
  - 另一方案：管理员重设也直说「与对方最近 5 次使用过的口令相同」（前端 v0.4 原型文案）。否决。管理员知道自己输入的是什么，但不知道它是不是对方用过的口令。直说原因，系统就成了可以反复试探对方历史口令的探针；本篇不加次数限制，试探也不受限；而人常在别处复用旧口令。本人改密不存在这个问题，所以只在本人改密时返回 `reused`。前端管理员重设处的文案应为「此口令不可用，请换一个」，「与最近 5 次相同」只用在本人改密。这是对前端原型的影响，不在本篇改。
  - 残余：`unavailable` 只会在其余可公开规则都通过时出现，管理员仍能推断出被拒的原因不在可公开规则之内。换成通用文案也一样，这一点无法避免，工程主管已接受。
  - 返回内容都不说明命中的是第几次。
- **首登强制改密**：重置和恢复写入的初始口令本身也要过历史校验。它成为当前口令后，人员首登强制改密时（GLOSSARY「强制改密」）又会被比较一次，所以不能改回管理员设的初始口令，也不能改回自己之前的口令。
- **存储**：新表见下节「建表与 G1 白名单」。只存被换下来的口令散列，当前口令仍在 `Personnel.passwordHash`（`backend/prisma/schema.prisma:76`）。换口令时，把旧散列追加进历史，再改当前，两步在同一事务里完成。旧散列为空就不追加。读取时按 `personnelId` 取 `retiredAt DESC, id DESC` 的前 `PASSWORD_HISTORY_DEPTH - 1` 条，加 `(personnelId, retiredAt)` 索引。因为只记换下来的口令，存量人员不需要回填。
- **只追加**：表上挂 `reject_row_mutation`，拒绝更新和删除（函数定义在 `backend/prisma/migrations/0002_identity_org/migration.sql:69`）。超出 N 的旧散列一直保留，不设定期删除的例外。这与 `docs/global-contract-identity-references.md:117` 的不物理删除，以及 #16、#49（`reset` 是唯一的删除入口）一致。比对只取最近 N 条。库泄露时旧散列越多暴露面越大，这一点已知并接受。
- **停用与恢复**：历史保留，恢复后照样拦截。这和 GLOSSARY「停用：只可恢复，不可删除」（`GLOSSARY.md:145`）以及人员只失效不删除一致。
- **并发**：散列和比较都放在事务外完成（与 #105「口令散列在事务之外计算」一致）。事务内以读到的 `Personnel.passwordHash` 为期望值，用条件更新（同 `replacePasswordHash`，`prisma-identity-store.ts:158-168`）。条件不成立说明期间有人改过口令，本次不写库，返回 409 `{ result: 'concurrent-change' }`。同一个人两次并发改密，最多只有一次成功。#105 目前没有成文的错误码表，正文只写「409 和可读原因」。码名按代码里已有 `result` 的短横线写法起（`invalid-credential`、`capacity-reached`、`non-compliant`）。重做 spec 时把它并入 #105 的错误码表。
- **性能**：每次最多验证 5 次 argon2，在线程池里执行，耗时可以接受。登录路径不受影响。
- **留痕**：成功时沿用 ADR 0011 已有的 `account.password-changed`、`account.password-reset`。写历史表本身不单独写留痕。
  - 被拒时按实际原因留痕。现有取值不够用：`account.password-reset` 和 `account.password-changed` 只记成功（`packages/audit/src/vocabulary.ts:2-8`），表外的动作和原因会被 `assertVocabulary` 拒绝（`packages/audit/src/prisma-audit-trail.ts:33-43`）。
  - 所以给 ADR 0011 追加一个记失败的动作 `account.password-rejected`，原因取 `reused`（系统管理重置口令、恢复时重置初始口令命中历史）或 `concurrent-change`（任一入口的 409）。
  - 字段：操作者、被作用人员、工号快照、对方当时的任职机构、来源地址、操作码（`personnel.password.reset`、`personnel.restore`，本人改密为空）、原因。口令、散列、前值都不记。
  - 这次拒绝没有业务写入，留痕在业务事务之外写。#105 实施决定已写明「拒绝类留痕……在业务事务回滚之后另起事务写入」。本人改密命中历史、可公开规则不合规，与现状一样不写留痕。
  - 改动只涉及 `vocabulary.ts` 加一个动作和一组原因、`port.ts` 加一个联合成员，再在 ADR 0011 的取值清单里追加一句，写法同 `login.capacity-reached`（「2026-10-15 追加，见 #91」）。
  - 不改记应用日志。原因：backend 现在没有应用日志设施，日志也不能永久查阅；#105 还要求每个 409 用例断言失败留痕行存在。
- **测试接缝**：散列与验证经 `CredentialService` 注入；历史读写在 `IdentityStore` 上新增 `listRecentPasswordHashes(personnelId, limit)`，换口令改为 `rotatePasswordHash(personnelId, expectedHash, newHash, at)`（追加历史 + 条件更新，在同一事务里）。N 经构造参数注入，默认用常量，测试里可以传 2。
- **行为测试**（HTTP 响应、库里的行、留痕行）：
  - 连改 5 次后，第 1 次的口令重新可用，第 2 到第 5 次的口令和当前口令都被拒绝。
  - 本人改成当前口令，只返回 `same-as-current`；改成历史口令，返回 400，`rules` 含 `reused`，响应里没有序号，不写留痕。
  - 系统管理重置口令时，用当前口令或最近 4 条历史中的任一个，都返回 400 `rules: ['unavailable']`，响应里不出现 `reused`；`Personnel` 行不变；写一行 `account.password-rejected`（`outcome=failed`，原因 `reused`，口令和散列不在任何一列），不写成功的 `account.password-reset`。
  - 恢复时重置初始口令命中历史：同上，返回 `unavailable`，留痕原因 `reused`、操作码 `personnel.restore`，人员仍为停用。
  - 重置口令同时违反长度等可公开规则时，只返回那些规则码，不做历史比对，也不出现 `unavailable`。
  - 重置后首登强制改密，改回初始口令被拒绝。
  - 停用、恢复后，用停用前的口令重置初始口令仍被拒绝。
  - 两个请求并发改密：一个返回 200，另一个返回 409 `concurrent-change`；历史只多一行；当前散列是成功那一次的；失败一方有一行 `account.password-rejected`，原因 `concurrent-change`。
  - 被拒绝时，历史表和 `Personnel` 都不变；历史表的 UPDATE、DELETE 被触发器拒绝。
  - 历史条目带旧 argon2 参数时，仍能命中。
- 术语见 `GLOSSARY.md` 的「口令」「重置口令」（「人员与登录凭据管理」词条）「停用」「强制改密」。

## 建表与 G1 白名单

- **流程**：#47 规定 G1「地基不含业务实体」不可扩大，CI 结构测试与评审是两道闸。结构测试注释写明，白名单外新增 model 即红，「逼建表动作回到 #47/#16 定案票」（`tools/structural-test.sh:399-401`、`:441`）。名单与实际 model 必须逐字相等，缺一个也红（`:402`、`:449`）。所以先回定案票留痕，再把建表迁移、`schema.prisma` 和白名单放在同一个 PR 里，与 #69 追加 `AuthSession`、`AuthRememberMe` 的做法一样（#75 回写评论也要求同一 PR）。
- **表**：Prisma 模型 `PersonnelPasswordHistory`，库表名 `personnel_password_history`。
  - `id` String（ULID，主键）
  - `personnelId` String → `Personnel.id`，`@map("personnel_id")`
  - `passwordHash` String，PHC 串，`@map("password_hash")`
  - `retiredAt` DateTime `@db.Timestamptz(6)`，`@map("retired_at")`，表示这个口令被换下的时刻
  - 索引 `(personnelId, retiredAt)`
  - 迁移里给这张表挂 `reject_row_mutation` 触发器，拒绝 UPDATE 和 DELETE
- 不改其他表。`Personnel` 不加列。
- **白名单改法**：在 `tools/structural-test.sh` 的 `G1_MODELS` 数组（`:407-424`）里，`AuditTrail`（`:421`）之后加一行 `  PersonnelPasswordHistory`；在白名单上方的追加记录注释（`:403-406`，「#69 定案追加…」「#92 定案追加…」「#96 …」）之后、`G1_MODELS=(`（`:407`）之前加一行 `# #75 定案追加 PersonnelPasswordHistory（ADR 0015）。`。#75 正文写的 `structural-test.sh:387-397`、9 个 model 已经过时，以现行行号为准。

## 工程已定（工程主管 2026-10-17）

1. 超过 5 条的旧散列一直保留，表只追加，不开定期删除例外；比对只取最近 N 条。见「只追加」。
2. 系统管理重置口令和恢复时重置初始口令命中历史时，不向管理员提示原因，只返回 `unavailable`；服务端用 `account.password-rejected` 按实际原因留痕；本人改密仍返回 `reused`；不加次数限制。前端 v0.4 原型的管理员重设文案随之调整。见「拒绝」「留痕」。
3. 并发冲突返回 409 `concurrent-change`，重做 spec 时并入 #105 错误码表。见「并发」。
4. 「当前口令 + 4 条历史」按 Lei Hu 授权由团队定，不再确认。见「口径」。
