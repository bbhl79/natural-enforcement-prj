**判读**：

- #76 说的「21 个字体对象中仅 3 个带 ToUnicode」在**数量级上不算离谱**（实测 12 个字体对象、3 个带 ToUnicode），但**这 3 个恰好是承载全部中文正文的那 3 个**，另外 9 个只是数字/拉丁字母壳。所以「只有 3 个带 ToUnicode」不构成「无法还原」。

用 `/ToUnicode` 作 CID→Unicode 源（内嵌 TTF `cmap` 反查作对照，结果 **0 汉字**，证明本文件的权威映射是 ToUnicode 而非字体表），441 页全部产出：

**#76 解码器为何会「提取为空」——本票踩过的同类坑（供复核其结论可靠性）**：本票第一版解码器同样得到 0 汉字，原因有三，且全是静默失败：

1. **未展开 `/ObjStm`**：页面/字体字典藏在 102 个对象流里，只扫常规对象会只看到 1,660 个对象、误判「字体不全/无资源」。
2. **十六进制字符串未做 hex→bytes**：本文件中文串以 `<0430 0431 …>` 形式出现，若把 ASCII 十六进制字符当字节流两两取码，得到的是**看似合理但完全错误的汉字**（本票中间产物曾输出「缆缓缆缆缆缓」这类乱码），比空结果更容易被误读为「轮廓化」。
3. **`/DescendantFonts 14 0 R` 指向的是一个数组对象 `[15 0 R]`**，不解引用就拿不到 `FontDescriptor`/`FontFile2`。

即：**「提取为空」是解码器缺陷的症状，不是文档属性。**

### 3.1 试行稿侧事实 —— 已查证（一手）

### 3.2 正式版侧事实 —— 转引交叉印证

#67 与 #76 争的就是这一侧。用**两票共同引用的那篇解读本**（`secrss.com/articles/23711`，正式版三级**网络设备**身份鉴别单元）核对：

### 3.3 判定：#76 的「互斥」诊断不成立

`L3-CES1-03` 与 `L3-ADS1-05` **不是同一件事的两个候选编号**，三层都不重合：

1. **不同版本**：前者属正式版 28448-2019 编号体系，后者属 2017 试行稿编号体系。
2. **不同安全类**：`CES` = 正式版「安全计算环境」；`ADS` = 试行稿「应用和数据安全」。试行稿把设备与应用拆成 `ECS`/`ADS` 两类，正式版合并为一类，所以两套体系**并行存在、各自自洽**，不是二选一。
3. **不同测评项**：按 #76 自己引的那份来源，`L3-CES1-03` 的内容是「远程管理防窃听」，与「双因子」无关；双因子在正式版设备侧是 `L3-CES1-04`，在试行稿应用侧是 `L3-ADS1-05`。

→ **#76 的「两套编号不能同时成立」是把不同版本、不同安全类、不同测评项的三个编号误当成同一项的竞争标注，属误诊。二者完全可以同时成立。**

**同时保留一条诚实的反向信号（不夸大为结论）**：该解读本在**网络设备**侧的四个单元中**没有**「首次登录强制修改初始口令」项。这**不能**证明正式版应用侧也没有（该文对象仅为网络设备，且正式版应用系统侧单元本票未取到），但它确实削弱了「试行稿 L3-ADS1-03 会原样进入正式版」这一假设。因此：

- 「试行稿有 L3-ADS1-03」→ **已查证（一手）**。
- 「正式版有对应单元」→ **确认无法获取（附原因：正式版全文反爬/付费未取得；唯一二手来源在设备侧未见此条）**。
- #67 §2.2「正式版编号体系经交叉印证一致」与 §6.1「② 正式版编号体系 L3-CES1-01~04…与试行稿内容对应一致」的表述**过强且指向错类**：`L3-CES1-01~04` 对应的是试行稿 **`L3-ECS1-01~04`**（设备和计算安全），不是 `L3-ADS1-*`（应用和数据安全）。
