# 代码注释约定

本文件说明本仓库源码注释的写法。注释服务两类读者：人类维护者与 agent。结构测试 `tools/structural-test.sh` 的 `source-comment-coverage`、`shell-comment-coverage`、`comment-path-refs` 三条规则按本约定做机器检查。规则只检查 `COMMENT_SCOPE` 范围内的文件。

## 1. 适用范围

- 纳入：`backend`、`packages`、`frontend/src`、`integration`、`e2e`、`tools`、`infra`、`dev`，含测试文件。
- 排除：Markdown 文档；JSON 数据；Prisma schema 与 `backend/prisma/migrations`（迁移文件改动会改变校验和）；`*.generated.ts`；`backend/prisma/generated`；`frontend/prototype`；`frontend/dist`；`e2e/results`。
- 范围只升不降。目录一旦纳入 `COMMENT_SCOPE`，就必须长期保持合规。

## 2. 基本原则

- 注释说明代码做什么、被谁调用、依据哪个来源、有哪些不能破坏的约束。
- 不逐行解说。不复述函数名或类型。不写改动历史，历史留在 git log 与 Issue。
- 不在注释中重新解释业务规则。业务规则的解释权在飞书权威文档与项目负责人。注释只写「代码做什么」和「依据来源」。
- 拿不准时写「待确认」，并指向来源。
- 引用只指向已入库文件（以 `git ls-files` 为准）。
- 注释里不得出现 import 样式文字：`from`、`import`、`require` 之后跟引号与 `@natural-enforcement/` 或相对路径。依赖矩阵规则按文本扫描 import，不区分注释与代码，这类文字会被判为真实导入，整个结构测试与 `./dev lint` 会变红。写调用方时只写路径，例如 backend/server/src/app.module.ts，不要带引号。
- 注释中的真人姓名改写为角色或职务。
- 注释使用简体中文。标识符、路径、操作码、Issue 编号保持原文。
- 不写「本轮」「本期」这类时效词。

## 3. 文件头（非测试源文件）

```ts
// 用途：<业务上做什么，一句话>
// 调用方：<谁调用：入口、服务或页面，写路径；仅模块内部用时写「本模块内部」>
// 边界：<不做什么；需要时写同事务、失败语义、权限点；没有则省略>
// 依据：<GLOSSARY 词条、docs/adr/NNNN、docs/research/、规格或 Issue 编号；至多 3 个>
// 待确认：<可省；格式「待确认：<问题>，来源 <…>」>
```

- 「用途：」为必填项。机器检查：文件开头的注释区内须有「用途：」行。
- 其余行按优先级补充：
  - P0（规则与入口：规则判定、状态机、授权、留痕、对外接口、启动装配）：须填调用方、边界、依据。
  - P1（服务、控制器、页面与 loader）：填用途与调用方。
  - P2（类型、常量、纯工具函数）：只填用途。
- 「依据」的编号至多 3 个。
- 写法参考：`backend/case/src/clue/closure/no-case-from-filing.ts` 的头部写明了调用方与同一事务的约束。

## 4. 导出符号

紧邻导出声明写 JSDoc 或 `//` 注释。第一句说明做什么。需要时补充失败语义（返回的原因码）、副作用（写哪些表、留痕哪个动作）和调用方。

「紧邻」的定义：

- 注释的最后一行与声明之间不得有空行，也不得有代码行。
- 装饰器行（`@Controller(...)`、`@Injectable()`）可以夹在注释与声明之间。
- 文件头注释不算第一个导出符号的注释。文件头与第一个导出之间有空行时，导出符号仍须另写紧邻注释。
- 分节分隔线（如 `// ---- 服务 ----`）不是对符号的说明。分隔线后面的导出符号仍须另写紧邻注释。
- 再导出（`export type { A } from '…'`、`export { A } from '…'`、`export * from '…'`）不要求注释。

```ts
/**
 * 授权入口：按操作码判定操作者对某机构范围内资源的权限。
 * 拒绝时先追加一行 authz.denied（自成事务），再抛 AccessDeniedError。
 * 只做判定的场景用 check：它交出留痕行，由调用方在业务事务回滚后写入。
 * 调用方：各业务服务的读写入口，例如 backend/server/src/clue-dispatch.service.ts。
 */
```

## 5. 控制器路由

每个路由装饰器的紧邻上一行写一条 `//` 注释：做什么；操作码；对象级权限或例外。

```ts
// 读取线索的核查状态与历史运行；操作码 clue.read。
@Get('clues/:id/verification')
```

- 操作码写作「操作码 」加一个空格，再加操作码。操作码必须是 `packages/shield/src/contract/opcode.ts` 登记表中的键。机器检查：注释中的操作码须在登记表内。
- 路由不经操作码授权时，写「无操作码（<原因>）」。机器检查只要求括号内有原因。常用原因：「登录前」「仅需登录会话」。
- 登记表不全是字面量：`cfg.<对象>.<动作>` 由 4 个对象与 5 个动作组合生成。规则已展开这 20 个码，注释可以直接写。
- 一条路由在服务内按条件走不同操作码时，注释写主路径的操作码，并在同一行说明另一个码。机器检查只取第一个「操作码 <码>」。
- 操作码以服务内的 `authorize` 或 `check` 调用为准，沿「控制器 → 服务」追踪得出。追踪不到时写「待确认：操作码，来源 <服务文件>」，不得猜测。

## 6. 前端

- 页面组件、loader、action：文件头写路由或菜单位置、调用的接口（写作 `METHOD 路径`）、需要的操作码或角色。
- API 函数：函数注释写 `METHOD 路径` 与操作码。文件头已经说明行为的，函数注释指向文件头。
- 前端导出符号按第 4 节检查。P1 只写一行，不写 `@param`、`@returns`。

## 7. 测试

- 每个 `describe(` 紧邻上一行写一条注释：这组用例验证的业务意图，引用 Issue 或规则编号。不复述 `it` 的标题。机器检查：`describe(` 的紧邻上一行须是注释。
- 测试辅助函数（`.test.` 文件之外、导出的函数）按第 4 节写 JSDoc，说明造什么数据、写哪些表。

## 8. Shell

适用于 `dev`、`tools`、`e2e`、`integration` 下的 `.sh` 文件，以及 `dev` 本身。

- 文件头写用途、用法入口、退出码（如有）。机器检查：文件头须有「用途：」行。
- 每个函数定义紧邻上一行写注释：做什么、参数、副作用。机器检查：函数定义的紧邻上一行须是 `#` 注释。
- `dev` 的帮助输出（`usage`）不随注释批次改动。帮助文字的修正另起 PR。

## 9. 注释 PR 的边界

- 注释 PR 只改注释，不改代码行。
- 一个 PR 按模块划分，不超过 30 个文件。
- Issue 编号：文件头至多 3 个，函数注释至多 1 个。既有编号保留，作为依据尾注。

## 10. 加入检查范围

在 `tools/structural-test.sh` 的 `COMMENT_SCOPE` 中加入新完成的目录，然后运行 `./dev lint`。结构测试通过后，该目录即受机器检查保护。
